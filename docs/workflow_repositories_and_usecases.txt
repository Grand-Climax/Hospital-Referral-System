 SECTION 1: DOMAIN INTERFACE PACKAGES
================================================================================

Package path: internal/domain/interfaces/repository/
Package path: internal/domain/interfaces/usecase/

which allows any package to import a single alias:

  irepository "Hospital-Referral-System/internal/domain/interfaces/repository"

FILE: base_repository.go
  Interface : BaseRepository[T any]
  Methods   : Create, FindByID, FindAll, Update, Delete
  Purpose   : Generic CRUD interface. All domain-specific repositories embed
              this so they inherit standard operations without re-implementing.
  Usage     : Embedded by every repository interface (e.g., TriageQueueRepository
              embeds BaseRepository[entity.TriageQueue]).

FILE: triage_repository.go
  Interface : TriageQueueRepository
  Entity    : entity.TriageQueue
  Methods   :
    Create(ctx, *TriageQueue) error
    GetByReferralID(ctx, referralID) (*TriageQueue, error)
    GetByHospitalAndStatus(ctx, hospitalID, status) ([]TriageQueue, error)
    Update(ctx, *TriageQueue) error
    DeleteByReferralID(ctx, referralID) error
    ListForTriage(ctx, hospitalID, limit, offset) ([]TriageQueue, int64, error)
  Purpose   : Manages the priority queue of accepted referrals waiting to be
              scheduled at the target hospital.
  Usage     : Called by TriageUseCase when a referral is accepted (LandInQueue),
              when the specialist reviews the queue (ReviewTriage), and when
              a patient arrives (ArrivalUseCase.ConfirmArrival).

FILE: ml_prediction_repository.go
  Interface : MLPredictionRepository
  Entity    : entity.MLPrediction
  Methods   :
    Create(ctx, *MLPrediction) error
    GetLatestByReferralID(ctx, referralID) (*MLPrediction, error)
  Purpose   : Stores severity scores returned by the external ML service
              (triggered by the specialist via RerunML).
  Usage     : Read by TriageUseCase.CalculateCompositeScore to factor ML severity
              into the triage priority formula. Written by ReferralUseCase when
              the ML service responds.

FILE: scheduling_repository.go
  Interfaces:

  DailyScheduleRepository
  Entity    : entity.DailySchedule
  Methods   :
    Create(ctx, *DailySchedule) error
    GetByHospitalAndDate(ctx, hospitalID, date) (*DailySchedule, error)
    IncrementBookedSlots(ctx, id, version) error   ← optimistic locking
    Update(ctx, *DailySchedule) error
  Purpose   : Tracks appointment slot usage per hospital per day.
              IncrementBookedSlots uses an optimistic lock (version column) to
              prevent double-booking under concurrent scheduling requests.
  Usage     : SchedulingUseCase.ScheduleAppointment reads the slot count,
              validates capacity, then increments atomically inside a transaction.

  SchedulerCheckpointRepository
  Entity    : entity.SchedulerCheckpoint
  Methods   :
    GetLastCheckpoint(ctx) (time.Time, error)
    UpdateCheckpoint(ctx, timestamp) error
  Purpose   : Tracks the last time a background scheduler job ran (e.g., the
              missed-arrival detector). This is a scheduling concern, NOT an
              admin concern, so it lives here.
  Usage     : The background cron job reads the last checkpoint, processes all
              events since then, then writes an updated checkpoint timestamp.

────────────────────────────────────────────────────────────────────────────────
FILE: capacity_override_repository.go
  Interface : CapacityOverrideRepository
  Entity    : entity.CapacityOverride
  Methods   :
    Create(ctx, *CapacityOverride) error
    GetActive(ctx, hospitalID, date) (*CapacityOverride, error)
  Purpose   : Stores temporary capacity overrides set by hospital admins.
              An override allows scheduling beyond the default MaxSlots limit
              for a specific date (e.g., to handle surge demand).
  Usage     : SchedulingUseCase.ValidateCapacity checks for an active override
              before rejecting an appointment due to capacity.
              AdminUseCase.ManageCapacityOverride creates overrides.

FILE: referral_repository.go
  Interfaces (all referral-domain concerns live in one file):

  ReferralRepository        — core referral CRUD + role-based query methods
  ReferralOutcomeRepository — records clinical outcome when episode ends
  ReferralRedirectionRepository — logs when a referral is redirected
  ReferralAccessRepository  — tracks per-doctor access grants (treating / consulted)

  ReferralOutcomeRepository
  Entity    : entity.ReferralOutcome
  Methods   :
    Create(ctx, *ReferralOutcome) error
    GetByReferralID(ctx, referralID) (*ReferralOutcome, error)
  Purpose   : Each completed referral episode ends with a recorded outcome
              (e.g., TREATED, DECEASED, TRANSFERRED). Immutable once created.
  Usage     : ClinicalUseCase.RecordOutcome writes this record and sets the
              referral status to COMPLETED.

  ReferralRedirectionRepository
  Entity    : entity.ReferralRedirection
  Methods   :
    Create(ctx, *ReferralRedirection) error
    GetByReferralID(ctx, referralID) (*ReferralRedirection, error)
  Purpose   : When a referral cannot be handled and must be sent to a different
              hospital or department, a redirection record is created.
  Usage     : Future use — the redirection workflow creates this record before
              re-routing the referral to a new target.

  ReferralAccessRepository
  Entity    : entity.ReferralAccess
  Methods   :
    Create(ctx, *ReferralAccess) error
    GetAccess(ctx, referralID, doctorID) (*ReferralAccess, error)
  Purpose   : Controls which doctors can view or update a referral beyond the
              primary specialist. An AccessType enum distinguishes TREATING_DOCTOR
              from CONSULTED_DOCTOR.
  Usage     : Created when a specialist grants another doctor read/update access
              to a referral for consultation.

  Interface : ClinicalUpdateRepository
  Entity    : entity.ClinicalUpdate
  Methods   :
    Create(ctx, *ClinicalUpdate) error
    ListByReferralID(ctx, referralID) ([]ClinicalUpdate, error)
  Purpose   : Stores ongoing clinical progress notes added by the treating doctor

  Usage     : ClinicalUseCase.AddClinicalUpdate creates notes.
              ClinicalUseCase.GetClinicalHistory lists them for the timeline view.

────────────────────────────────────────────────────────────────────────────────
FILE: notification_repository.go
  Interface : NotificationRepository
  Entity    : entity.Notification
  Methods   :
    Create(ctx, *Notification) error
    GetQueued(ctx, limit) ([]Notification, error)
    UpdateDelivery(ctx, id, status, messageID) error
  Purpose   : Manages the outbound SMS notification queue. Notifications are
              created with status QUEUED and then bulk-sent by a cron trigger.
  Usage     : NotificationUseCase.QueueNotification creates entries.
              NotificationUseCase.TriggerManualSend reads queued entries, calls
              the AfroMessage SMS client, and updates delivery status.
              NotificationUseCase.HandleSMSWebhook updates status from callbacks.

FILE: admin_workflow_repository.go
  Interface : SystemConfigRepository
  Entity    : entity.SystemConfig
  Methods   :
    GetByKey(ctx, key) (*SystemConfig, error)
    GetAll(ctx) ([]SystemConfig, error)
    Update(ctx, *SystemConfig) error
  Purpose   : Key-value store for runtime system configuration (e.g., aging_factor
              used in triage scoring, default slot capacities, feature flags).
  Usage     : TriageUseCase reads aging_factor to calculate composite scores.
              AdminUseCase.UpdateSystemConfig writes new values via the admin API.

  NOTE: StaffReplacementLog is managed by UserRepository (already existed).
        SchedulerCheckpoint is managed by SchedulerCheckpointRepository in
        scheduling_repository.go.

FILE: triage_usecase.go
  Interface : TriageUseCase
  Methods   :
    LandInQueue(ctx, referralID) error
    CalculateCompositeScore(ctx, referralID) (float64, error)
    ListForTriage(ctx, hospitalID, limit, offset) ([]TriageListResponse, int64, error)
    ReviewTriage(ctx, referralID, userID, TriageReviewRequest) error
  Purpose   : Orchestrates the triage priority scoring pipeline.
              When a referral is accepted by a specialist, LandInQueue is called
              to place the patient in the hospital's priority queue with an
              initial composite score.
  Score formula: (clinical_severity × 0.6) + (ml_severity × 0.3) + aging_bonus

────────────────────────────────────────────────────────────────────────────────
FILE: scheduling_usecase.go
  Interface : SchedulingUseCase
  Methods   :
    GetCapacityStatus(ctx, hospitalID, dateRangeDays) ([]CapacityStatusResponse, error)
    ScheduleAppointment(ctx, referralID, userID, SchedulingRequest) error
    ValidateCapacity(ctx, hospitalID, date, override) (bool, error)
  Purpose   : Handles manual appointment scheduling for queued referrals.
              Uses a database transaction + optimistic locking to prevent
              double-booking when multiple specialists schedule simultaneously.
  Usage     : The specialist reviews the capacity calendar, picks a date, and
              submits a schedule request. The usecase validates capacity (with
              override if allowed), increments booked_slots atomically, updates
              the triage queue record's appointment_date, and advances referral
              status to SCHEDULED.

────────────────────────────────────────────────────────────────────────────────
FILE: arrival_usecase.go
  Interface : ArrivalUseCase
  Methods   :
    MarkExpected(ctx, referralID) error
    ConfirmArrival(ctx, referralID, receptionistID) error
    UpdateArrivalStatus(ctx, referralID, status) error
  Purpose   : Manages the physical arrival of a patient at the reception desk.
              MarkExpected is called on appointment day to update the status to
              EXPECTED. ConfirmArrival is called when the patient physically
              arrives (sets ARRIVED + timestamp). UpdateArrivalStatus handles
              edge cases (MISSED, ADMITTED).
  Usage     : Receptionist handler calls ConfirmArrival. The background cron
              job calls UpdateArrivalStatus(MISSED) for no-shows.

────────────────────────────────────────────────────────────────────────────────
FILE: clinical_usecase.go
  Interface : ClinicalUseCase
  Methods   :
    AddClinicalUpdate(ctx, referralID, userID, ClinicalUpdateRequest) (*ClinicalUpdateResponse, error)
    RecordOutcome(ctx, referralID, userID, ReferralOutcomeRequest) (*ReferralOutcomeResponse, error)
    GetClinicalHistory(ctx, referralID) ([]ClinicalUpdateResponse, error)
  Purpose   : Manages clinical data during the active episode.
              Treating doctors add progress updates throughout the referral.
              When care is complete, RecordOutcome finalizes the episode and
              marks the referral as COMPLETED.
  Usage     : Called from the clinical handler (protected by specialist/doctor role).

────────────────────────────────────────────────────────────────────────────────
FILE: notification_usecase.go
  Interface : NotificationUseCase
  Methods   :
    QueueNotification(ctx, referralID, notifType, message) error
    TriggerManualSend(ctx) (*NotificationSendSummary, error)
    HandleSMSWebhook(ctx, messageID, status) error
  Purpose   : Orchestrates outbound SMS notifications.
              QueueNotification creates a QUEUED record; TriggerManualSend is
              called by the internal cron endpoint to bulk-send pending messages
              via the AfroMessage SMS API; HandleSMSWebhook processes delivery
              receipts from the SMS provider callback.
  Usage     : Other usecases call QueueNotification to schedule patient/doctor
              SMS alerts (e.g., appointment confirmation, arrival reminder).
              The internal cron route calls TriggerManualSend on a schedule.

  Interface : AdminUseCase
  Methods   :
    UpdateSystemConfig(ctx, userID, map[string]string) error

 SECTION 4: CONCRETE IMPLEMENTATIONS  →  internal/repository/
================================================================================

ALL new repository implementations embed *BaseRepository[EntityType] following
the established pattern in user_repository.go and hospital_repository.go.

This means:
  - The struct gets Create/FindByID/FindAll/Update/Delete for free
  - Domain-specific methods are added on top
  - The struct has BOTH a db field (for custom queries) and the BaseRepository
    (for generics), e.g.:

  type triageRepository struct {
      *BaseRepository[entity.TriageQueue]
      db *gorm.DB
  }

File mapping:
  triage_repository.go           → triageRepository
  ml_prediction_repository.go    → mlPredictionRepository (NEW, own file)
  scheduling_repository.go       → dailyScheduleRepository, schedulerCheckpointRepository
  capacity_override_repository.go → capacityOverrideRepository (NEW, own file)
  referral_repository.go         → referralRepository (existing) +
                                   referralOutcomeRepository (moved here) +
                                   referralRedirectionRepository (moved here) +
                                   referralAccessRepository (moved here)
  clinical_workflow_repository.go → clinicalUpdateRepository only
  notification_repository.go     → notificationRepository only
  admin_workflow_repository.go   → systemConfigRepository only
  user_repository.go             → (unchanged) userRepository +
                                   CreateStaffReplacementLog method
